实现范围
--------
vision_grasp_baseline/run.sh collect 现在默认使用完整轨迹执行。每轮流程：
人工复位方块并按回车 -> 新 RGB-D 检测 -> 规划/确认机械零位并张开夹爪
-> 零位重新检测 -> 一次生成抓取、入盒、回零的全部路径 -> 连续化和重新定时
-> 检查控制器实际五次插值路径，保存完整轨迹 -> 再检测并核验场景
-> continuous-check在无运动租约下完成新场景全路径预检，保存与文件哈希绑定的证明
-> 开始记录 -> 按同一时间轴执行机械臂与夹爪 -> 实际回零 -> 停止记录
-> 视觉验收入盒 -> 人工审核并保存。

执行中不再规划，不调用逐段grasp-test / observe / waypoint-place-test / zero-test。
取消四个共线中间点的停车；夹爪开合保留必要的静止动作和各0.15秒稳定时间。
本次配置开合各约1.77秒。开合前检查实际TCP到位；持续保留反馈、实际状态碰撞、STOP保护。
20:32修复后，连续回放的TCP跟踪误差仅记录，不再以25mm/0.2秒阈值直接停机；
用目标50Hz的实际CAN姿态碰撞查询和URDF硬限位检查替代。采样检查不等于连续碰撞保证。
不再停下来做中途抬升拍照；最终入盒视觉验收和人工成功审核仍为导出必要条件。
默认每轮按新识别结果重新生成完整轨迹；也支持严格场景核验后的缓存回放。

collect 默认需要30条成功、人工确认的 episode；异常立即停止，已保存轮次不覆盖。
不是无人值守循环：每次入盒后要把方块取出、放回原来盒外的桌面位置。
盒子不移动。每轮仍重新识别，不复用上轮方块坐标。
相对首轮检测：方块三维中心偏差<=4cm；盒中心XY偏差<=2cm；盒yaw偏差<=0.15rad。
这是允许检测噪声和人工复位误差的门限，不是要求主动移动盒子2cm。
两臂开始记录时各7关节必须在机械零位±0.06rad内；末尾也复核反馈。
回零前不再把初始检测场景覆盖到已入盒的场景，避免方块障碍物错误回到桌面。

频率与图像约定
--------------
底层ROS控制：保持当前100Hz配置。完整路径重新定时，不沿用3%速度/1%加速度缩放。
TOPPRA约束路径速度，平滑加速度转换，再以Bernstein界检查JTC五次插值的速度、
加速度、加加速度及位置极值；超限时整体重新定时。使用已安装MoveIt配置与实机URDF
取交集的关节限制，目前右臂加速度0.5rad/s²、jerk 5rad/s³。
额外桌面高度余量15mm仅用于自由空间接近和回零规划，给平滑轨迹留余量；
接触抓取及最终完整路径碰撞检查仍使用原测量桌面和3mm顶面余量。
动作执行端不额外滤波、截断或修改已验证轨迹；实际输出仍作为训练标签。
实测关节：订阅/joint_states，保留每条原始发布，目标约100Hz。
动作标签：JTC controller_state.output.positions，按右臂控制器原始消息产生。
配置文件写state_publish_rate=50，但17:40这次实机记录实际约100Hz，以quality.json为准。
另外保存reference/feedback/output全部控制器消息；不是把实测q当作指令q。
RGB-D/腕部彩色：640x480，目标30Hz。SDK序列号344322073972；腕部by-id路径见元数据。
RealSense持续占用一个pipeline；识别、抬升验证、入盒验证从该pipeline取新鲜RGB-D。
连续RGB保存JPEG质量90；深度仅保存识别/验收快照，不逐帧保存全程深度。
ACT数据：30Hz、16维状态/动作、两个640x480 RGB图像，保留原始视野比例。
顺序：右臂7+右夹爪，左臂7+左夹爪；相机名ceiling、wrist_right。
左夹爪没有活动JTC，沿用已有采集约定：开始时的实测保持位置作为恒定标签；
监控其漂移不得超过0.03rad。元数据明确标注，不能把它解释成受控专家示教。
后续实机ACT仍只执行右侧8维，不把未示教的左夹爪输出接到执行器。

schema_version=2：ROS采用源header加固定偏移映射到CLOCK_MONOTONIC；另存到达时间。
控制器各自独立记录target_*.jsonl，保存时按源时间戳因果对齐成16维动作。
订阅RELIABLE、KEEP_LAST=256；记录器容许最多0.5秒传输回补，超过则失败。
最终仍按源时间检查状态最大间隔50ms、动作100ms，不插值、不伪造缺失样本。
执行端既有反馈保护未改动。图像编码/JSON落盘通过有界后台队列，队列溢出判失败。
RealSense设备时间/帧号单独保存。腕部只有软件读取序号，没有硬件帧号。
这不是硬件同步相机；导出在30Hz网格上选“不晚于网格时刻的最近样本”。
不把30Hz图像复制成100Hz来宣称更多视觉样本。
质量门：状态平均>=60Hz/最大间隔50ms；动作平均>=35Hz/最大间隔100ms；
每台相机平均>=25Hz/最大间隔150ms；所有流必须覆盖episode头尾±150ms。
数据质量、入盒、回零和人工确认都通过，才允许正式导出。

频率依据
--------
原始ACT仓库的仿真常量DT=0.02，即50Hz；这不是ACT模型对所有硬件的强制频率：
https://github.com/tonyzhaozh/act/blob/main/constants.py
LeRobot官方ACT示例相机使用30fps：
https://github.com/huggingface/lerobot/blob/main/examples/tutorial/act/act_using_example.py
本地DORA图dataflow-real-act-two-camera-host.yaml也是相机33ms tick、控制100Hz配置。
这里仅参考时间契约，不启动该图的直接CAN驱动；ROS继续独占电机控制。
实际安装的openarm_bimanual_moveit_controllers.yaml为100Hz、splines插值、JTC状态50Hz。
本次实测相机结果支持30Hz；更高机器人原始频率用于检查轨迹，不改变训练网格。
以后ACT推理动作时间基准也应是30Hz；例如chunk_size=50覆盖约1.67秒。
